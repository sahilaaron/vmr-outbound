The password form is first because it is the one that works for everybody — a colleague on Outlook, on Gmail, or on a VMR address — while Google is an accelerator for people whose Google account is already the one VMR knows. Password-manager compatibility is a deliberate property of this markup rather than an accident of it: * a real `
` with named `email` and `password` inputs, so a manager recognises it as a login form and offers to fill and to save; * `autocomplete="username"` and `autocomplete="current-password"`, which are the tokens managers key on; * `type="email"` and `inputmode="email"` so a phone shows the right keyboard; * nothing that blocks paste — there is no `onpaste` handler anywhere in this file, which matters because the policy explicitly expects generated 30-character values; * `autofocus` on whichever field is empty, so the common case is one keystroke. The refused state re-renders this same template with `error` set, so a failed attempt cannot ship different form attributes than the page a manager first saw. There is no CSRF field, and that is correct: an anonymous caller has no session to forge against, so there is no token to bind to.
